# Section Architecture — estrutura da página

A estrutura responde à jornada; não é lista obrigatória. Toda seção precisa de função e conteúdo.

| Seção | Incluir quando | Omitir/adaptar quando |
|---|---|---|
| Hero | Sempre que a página exige orientação imediata | Não omitir mensagem/ação central; mudar composição |
| Prova social | Há depoimentos, avaliações, logos ou cases reais/autorizados | Não inventar prova nem usar logos sem permissão |
| Benefícios | Há valor específico para o público | Repetem funcionalidades sem explicar valor |
| Funcionalidades | Operação/capacidades fazem parte da decisão | Não acrescentam compreensão |
| Serviços | Existem opções/escopos distintos | Oferta única sem variação útil |
| Produtos | Catálogo/variações influenciam compra | Preço/disponibilidade não confirmados |
| Processo | Etapas/responsabilidades geram dúvidas | Processo simples, explicável em poucas linhas |
| Galeria | Mídia real/autorizada influencia decisão | Sem assets/direitos adequados |
| Portfólio/cases | Trabalho, autoria e contexto podem ser mostrados | Projeto conceitual sem identificação |
| Preços | Valores/planos estão aprovados e atuais | Valores variáveis/desatualizados |
| FAQ | Há dúvidas/objeções recorrentes | Perguntas genéricas para preencher espaço |
| Contato/agendamento | Há CTA de contato, reserva ou consulta | Formulário cria fricção sem benefício |
| Footer | Navegação, dados legais e canais precisam de localização | Ajustar ao escopo |

## Ordem

Considerar informação necessária antes da ação, complexidade/preço/risco, familiaridade da marca, tráfego, provas e conteúdo. Seções podem ser combinadas; não criar bloco para cada linha.

Para cada seção, registrar objetivo, mensagem, fatos/assets necessários, permissão, CTA/interação, mobile e critério de aceite.

## Integridade

Depoimentos/resultados devem ser reais, autorizados e contextualizados. Cases conceituais devem ser rotulados. Não usar falsa escassez, números fictícios ou blocos apenas para aumentar comprimento.
